# 超强增效剂蓝图机会监控

独立的 EVE Online 宁静服公开合同监控器，专门监控八种**超强型增效剂制造蓝图拷贝（BPC）**。它支持 Windows 本机界面和 GitHub Actions 云端运行，与根目录的通用现货/BPC扫描共用 Cloudflare 邮件中转，但扫描状态、估值和推送次数独立。

当前云端版有两条彼此独立的机会通道：

1. **制造利润机会**：判断买下蓝图后按当前材料与成品参考价制造，是否达到利润和 ROI 门槛。
2. **蓝图每流程价差机会**：不要求制造利润达标，只比较同种蓝图合同的“ISK/流程”，寻找明显低于其他同种合同的报价。

两条通道都允许同一有效机会重复提醒，并在邮件中显示“**已推送次数：第 N 次**”；制造通道和价差通道分别累计，不共用计数。

## 扫描流程

1. 默认读取 ESI 星域目录，逐星域读取公开合同分页。允许高安、低安和 00 交货；启用 `jita_only` 后才只接受吉他 4-4。
2. 按合同类型、价格、到期时间和体积做预筛。
3. EVE Ref 公共合同快照仅用于优先定位可能含目标蓝图的合同；最终物品、BPC 标志和流程数仍以 ESI 合同物品接口核验。
4. 已核验合同物品写入本地/云端状态，避免每轮重新请求全部旧合同。204、403、404 或空物品结果只暂存一段时间，之后会重新核验。
5. 对确认有效的目标 BPC，分别进入“制造利润”和“同种蓝图每流程价差”两套逻辑。
6. 发信前保存投递检查点。投递结果不确定时按 fail-closed 处理，不自动当作“未发送”重试，避免重复邮件。

某些星域或单份合同接口失败时会记录覆盖不完整；运行成功也不等于每一份全服合同都在本轮重新核验。

## 通道一：制造利润机会

配方来自仓库内的 [recipes.json](recipes.json)。`Planner` 会展开反应/制造链并按批次取整；最终采购原料按吉他足量卖单成本计算。成品参考价采用伏尔戈星域最近可用完整交易日向前七天的成交量加权均价，**不是即时可砸的吉他买单**。

估算口径：

```text
估算利润
= 成品参考收入
- 销售费用预留
- 蓝图合同总价
- 原材料采购成本
- 额外费用预留
```

默认门槛：

| 设置 | 默认值 |
|---|---:|
| 合同总价上限 | 20 亿 ISK |
| 每张最低剩余流程 | 50 |
| 每 50 流程最低利润 | 1 亿 ISK |
| 最低回报率 | 20% |
| 单批成品占七天成交量上限 | 25% |
| 销售费用预留 | 收入的 5% |
| 额外费用预留 | 每 50 流程 1000 万 ISK |
| 交货地点 | 默认不限定吉他 |

邮件按每 50 流程利润、总利润排序，每封最多 10 个机会。每个合同显示本通道累计推送次数。

### 制造估值边界

邮件中的利润是筛选估算，不应等同于最终可兑现净利润。当前模型：

- 显示 BPC 的 ME/TE，但材料展开尚未应用每张蓝图 ME/TE。
- 没有逐份计算建筑加成、真实安装费、设施燃料和实际运输报价。
- 角色技能和具体建筑条件没有完整进入成本公式。
- 多份合同各自通过销量门槛，不代表它们的产量可以同时按同一参考价全部卖出。
- 远地玩家建筑的停靠/取货权限仍需在游戏中核实。

## 通道二：超强增效剂蓝图每流程价差

价差通道直接从**已核验的目标 BPC 合同池**计算，不要求该合同先通过制造利润筛选。因此：

> 制造利润不达标，不会阻止一个明显低价的同种蓝图进入价差提醒。

对每一种超强增效剂蓝图：

```text
每流程价格 = 合同总价 ÷ 合同总流程数
```

程序把同种蓝图按每流程价格从低到高排列。最便宜的合同作为候选，主要参照是**下一份最便宜的同种合同**。

```text
每流程价差 = 下一档每流程价格 - 当前每流程价格

折算总价差 = 每流程价差 × 当前合同总流程数

折价率 = 每流程价差 ÷ 下一档每流程价格
```

默认要求：

| 条件 | 默认值 |
|---|---:|
| 其他可比同种合同 | 至少 2 份 |
| 当前报价相对下一档折价 | 至少 20% |
| 按当前合同流程折算总价差 | 至少 3000 万 ISK |

邮件同时显示：

- 当前合同总价、总流程、每流程价格
- 下一份最便宜同种合同的每流程价格
- 其他同种合同每流程价格中位数
- 可比合同数量
- 每流程价差
- 相对下一档折价率
- 按当前合同总流程折算的理论总价差
- 本通道累计推送次数

### 价差通道不是“保证套利”

“折算总价差”只是当前公开挂牌合同之间的价格断层，不代表存在真实成交买家，也不等于可立即兑现的利润。合同市场缺少类似现货市场的实时买盘深度，因此这条通道的作用是**发现异常低报价，供人工快速判断**。

后续若积累足够历史合同消失/存续数据，可以继续加入成交概率、挂牌时长和历史每流程区间，用于降低虚假高价参照。

## 重复推送与计数

云端使用两个独立频道：

- `booster-manufacturing`
- `booster-spread`

同一合同可以在两条通道同时出现，各自维护自己的累计次数。例如：

```text
制造机会：已推送第 2 次
蓝图价差：已推送第 5 次
```

成功发送后，该频道约 30 分钟内不再发送下一封；这只是频道级发送节流，不是“合同永久冷却”。只要合同仍有效且继续符合条件，以后仍可再次提醒。

若一次发送处于 `sending` 或 `unknown` 状态，程序不会自动再次发送该合同，以免实际已经发送成功但响应丢失造成重复邮件。

## 云端状态与防重复

`eve-booster-monitor-state` 分支的 `state.json` 是云端持久状态，主要保存：

- 已核验合同物品
- 星域扫描游标
- 临时不可用合同
- 扫描状态
- 旧版投递台账（兼容迁移）
- `push_state`：两个新频道的累计推送次数与投递状态
- 两条频道各自的下一次允许发信时间

状态分支不保存 EVE 刷新令牌或邮件 API Key。

升级到双通道版时，旧版已成功发送的制造机会会迁移为制造频道至少 1 次历史推送；价差频道从独立计数开始。

为了保护推送次数和防止重复邮件：

- `state.json` 为空、JSON 损坏或格式不匹配时，云端运行应直接失败，不自动重置台账。
- 发信前先把机会写为 `sending` 并持久化。
- 发信结果无法确认时保存为 `unknown`，后续不自动重复投递。

不要通过删除状态分支或清空台账来处理普通接口故障。

## ESI 缓存与故障诊断

扫描器会复用 ESI 的 ETag/缓存。云端双通道版对 JSON 解析增加了保护：

1. 若某个 ESI 路径的缓存或响应出现空内容/非 JSON，先删除该路径缓存并重试一次。
2. 第二次仍失败时，不再只输出模糊的 `Expecting value`，而应在日志中显示具体 ESI 路径。
3. `cloud_run.py` 的失败日志同时输出当时的扫描阶段，例如“读取各星域公开合同”“更新吉他材料价格与成品成交参考价”或“核验蓝图物品和剩余流程”。

这类错误只表示该轮扫描没有完整确认新机会；程序不会把失败轮次当作成功投递。

GitHub Actions 中还可能看到 Node.js 版本弃用 warning。只要 `actions/checkout`、`actions/setup-python` 步骤本身为 success，它属于 Action 运行时提示，不等同于本程序扫描失败。

## 扫描状态字段

| 字段 | 含义 |
|---|---|
| `regions_checked / regions_total` | 已尝试读取的星域数；失败详情见 `region_errors` |
| `coverage_complete` | 星域合同列表是否全部成功读取；不代表所有合同物品都已核验 |
| `scanned / candidates` | 候选中已有核验记录的数量与候选总数 |
| `new_inspected` | 本轮新取得物品/不可用结果的数量 |
| `item_errors` | 本轮合同物品请求错误数 |
| `pending` | 尚待核验数量 |
| `snapshot_target_contracts` | EVE Ref 快照识别的目标合同数，仅用于优先级 |
| `opportunities` | 当前制造利润达标合同数 |
| `spread_opportunities` | 当前每流程价差通道达标合同数 |
| `mail_error` | 最近邮件/授权相关错误 |

## Windows 本机界面

在 `booster-monitor` 目录使用 Python 3.11 或更新版本：

```sh
python -m pip install -r requirements.txt
python app.py
```

打开 `http://localhost:8787/`。本机界面仍基于 `app.py` 的基础制造监控逻辑；云端新增的双通道/重复计数逻辑由 `monitor_v2.py + cloud_run.py` 使用。

本机独立发信需要 EVE 应用 Client ID，回调为 `http://localhost:8787/oauth/callback`，权限为 `esi-mail.send_mail.v1`。授权角色必须是 LadyGuaGua。刷新令牌存入 Windows DPAPI 加密的 `data/mail-authorization.bin`；本机缓存和投递记录在 `data/monitor.sqlite`。整个 `data/` 不应上传公共仓库。

本机和云端状态彼此独立；若两边同时开启发信，可能产生重复提醒。
