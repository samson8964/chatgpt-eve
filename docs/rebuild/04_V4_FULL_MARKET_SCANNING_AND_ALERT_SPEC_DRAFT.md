# V4 全市场扫描、分级筛选与延迟推送详细设计 v0.1 — 待用户批准

**性质：审核草案，不是代码、部署或正式政策变更。** 从 V2/V3 继承授权、参数和已验证的经济常识，不复用其状态机、候选池、邮件判断或业务代码。

## 1. 不可修改的最高要求
1. **每轮完整独立新扫描：** 重新枚举全部预定可访问来源，获取它们全部可用订单及公开合同分页，生成新的 run_id 与带取得时间/ETag/Expires/校验摘要的 SourceSnapshot。历史状态不得决定某个商品、合同或来源是否被本轮跳过，也不得把上轮 CSV 冒充新数据。
2. **全量初筛：** 对本轮全部采集到的标的逐条执行标准化、最低可行性判断和经济上界测试；不得按历史 seen/last-TOP、单品历史搜索次数或固定数量先限额。
3. **深度验证与正式通知严格分离：** 初筛后有可能达到正式条件的所有候选都必须进入二次验证或记录明确的 PENDING_UNVERIFIED，不能因 CPU/API 时间预算隐式扔掉候选并宣布完成。
4. **只有新实例才首次通知：** 合同按 contract_id、市场按来源卖单/目的地买单 order_id 及数量/路线等形成 instance_key；每条实例的重算版本不等于新机会。历史不限制扫描，只控制同实例是否已发过。
5. **扫描和推送时钟独立：** 扫描尽可能按业务需要完整持续运行；通知可以2–4小时汇总一次。每次真发信前根据ESI允许的数据新鲜度重新验证。失效/利润不足/权限不足一律不发。
6. **覆盖不完整不许报全市场成功：** 某个来源缺页、403、429、5xx、过期或不一致，标记其 PARTIAL/FAILED；仅完整且自洽的无关来源有资格独立继续验证；任何依赖未完成订单簿的证明不能进入 MAIL。
7. **真实净利不是历史报价差额：** 采购用真实可成交卖单，退出用真实可成交买单，双侧深度与压力情景完整。含费用、运输、税、制造地点、流动性和角色参数。未知值不能自动解释为零。
8. **新旧隔离：** V4 与旧版共享已授权外部API/Worker、角色配置与Secrets引用，但扫描逻辑、持久状态、Outbox、代码命名空间全部独立。影子期没有真实发信资格。

## 2. 全市场覆盖边界（Coverage Registry）
**全市场 = 本项目可通过公共 ESI + 已经授权的 Upwell 建筑接口读取的完整可交易集合，不等于游戏里不可访问的所有私人建筑。**
- **S1 全服公开 item-exchange / 拍卖 / 运输合同目录：** 依据 API 可查询区域列表完整遍历 /contracts/public/{region_id}/ 全部页；将不符合策略的合同标 REJECT/RESEARCH，不能预先不抓。同一合同后续物品详情按需要批量获取，但所有挂牌必须进入初筛。
- **S2 全服 ESI 可查询公共区域市场订单：** 遍历覆盖注册表内所有公开星域市场 /markets/{region_id}/orders 全部页；保留每笔订单的 order_id、type_id、location_id、is_buy_order、price、volume_remain、range、issued、duration。将源卖盘/目的买盘索引化，准备可行路线比较。ESI 官方于2026-02-24对该接口引入 rate limiting；遵守官方分页、缓存头、退避和有意义 User-Agent。参考：https://developers.eveonline.com/blog/market-orders-rate-limit-rolls-out-on-february-24-2026
- **S3 已获访问权限的玩家建筑市场：** 4-H、C-J6MT、O4T-Z5 - Dracarys. Prime (SummerHall) 分别请求 /markets/structures/{structure_id}/ 全页；实际每轮检查 ACL/access_profile，不把可进入站点直接推定 ESI 可读取。玩家建筑订单通常不包含在区域订单API中。参考：https://docs.esi.evetech.net/docs/scenarios/structure_markets.html
- **S4 公共兑现与物流：** Jita、Amarr、Dodixie及有效全服买单作为可选退出点；按 route 的实际访问、站点、最大购买量、运输难度计算；不能把区域任意买单当作 Jita 4-4 的即时兑现金额。
- **S5 角色与研究侧：** 三角色持仓、钱包、个人合约、技能/税率授权范围与 EVE Ref/静态物品规格。角色私有来源不构成全服公开范围。静态类型映射可缓存；市场动态订单和合同不得用旧快照伪装新采集。

**快照要求：** 每次运行都发起本轮所需的完整 API 数据确认；在官方缓存生命周期内，允许合法 ETag/304 表示本轮验证“自上次版本未变化”，但必须写新的本轮确认时间，保留来源版本引用。不能为追求「每次新请求」规避官方缓存与限流。合同公开区域接口缓存可达约30分钟，市场订单常见缓存约5分钟；实际依响应 Expires/Cache-Control 记录而不是死设万能期限。分页在扫描期间可能变动，无法做到整个 EVE 市场跨星域的原子同时刻快照；以数据取得时窗、页集合/摘要、完整性校验明确界定观测结果。

## 3. 每轮实际执行算法（完整优先，不设固定Top上限）
**T0 运行开始：** 新 run_id/代码 SHA/policy_hash，锁住同一航道；拉取全部已批准 Coverage Registry，检查认证服务健康，清空本轮短暂内存变量（不清空合法历史账本）。
**T1 全量获取：** 并行限速拉取每个源的全部页，不能只取第一页/前1000个订单；记录 pages_expected/fetched、源响应时间、成功状态和API版本。上轮缓存只有按 ETag 确认有效才可引用。
**T2 构建全量索引：** 对本轮全部市场订单和合同字段去重、标准化、排除不可识别物品/不合法属性，保存完整本轮 universe。按地点+物品+买卖方向建立索引，避免O(N²)所有订单盲目两两匹配，但每个符合条件的订单必须进入索引。
**T3 所有标的做廉价预筛：** 对所有商品/合同计算基于最好可能成交价的 *上界利润*，执行显然不符合策略的安全筛除；上界必须保守地大于等于真实潜在利润才能用于排除。信息不足的项目不能用“上界=0”误筛，放入 NEEDS_PROOF。公开BPC、0运费/未知税率等不得被错认为立即兑现。
**T4 深度验证候选：** 对所有存在合格可能性的候选，按批次查询真实可成交订单簿（复用本轮仍有效的同一订单簿，不对单个商品盲目重复请求）；计算数量感知的买入/兑现 VWAP、双边深度、税费、运输、制造成本、最佳档消失后的压力结果及净收益。不能仅对“本轮排名前180/600”做深查。候选过多时允许延长任务、分批断点续跑；未验证完为 INCOMPLETE，不能把未处理候选视作已拒绝。
**T5 统一 Gate：** 每条得到不可变 ExecutionProof；仅已批准合格 MAIL 状态进入 Event Registry。保留 SAFE/WATCH/RESEARCH/REJECT 原因，形成按源的严格漏斗。
**T6 新旧实例对比：** *仅在 T5 后* 查询历史状态，按 instance_key 判断真正未通知的新机会。相同实例重算、TOP 名次变化、同一卖单报价变化不得重复首次提醒。对同一 type_id 真正新 order_id/买单的改变要判断其是否构成新的可执行实例。
**T7 写入 Outbox：** 通过事务唯一约束写事件，按收益、可执行概率、时间敏感程度排优先级；TOP10 是每封邮件的**展示上限**，不是候选池截断。第11至100条真正新的机会留在数据库待发，不能丢失。
**T8 扫描结算：** 保存 COMPLETE/PARTIAL/FAILED 每来源状态，扫描进度及原始快照索引、拒绝漏斗、新实例数，发布到工作台摘要；不因为无信而报失败，不因为扫描成功而报通知成功。

## 4. 出口模型与 Gate（沿用已批准规则）
- **合同直接兑现 FULL_CASH**：合同价+税费物流投入与真实可立即买单收入；完整深度覆盖、压力净利仍正。
- **部分现金底价 PARTIAL_CASH_FLOOR**：只计已证实立即兑现买盘，其余无法卖出项目估值0，不把“现金底价”包装为完整兑现；需要明确未兑现库存与损失风险。
- **跨站市场套利**：真实 source asks 买入、真实 destination bids 卖出，订单ID、数量、实际站点、min_volume/range、运输与安全风险，利润密度/风险成本。
- **BPC 制造**：真实 blueprint 合同价 + 材料卖单按量采购 + 设施安装/SCI/SCC + 税费/角色技能 + 往返运输 + 成品买单；且继承 Approved 严格 Gate。当前Issue#27 的版本冲突必须先由决策记录明确。
- **以物换物/高价值合同/保守挂卖**：各有独立成本和风险模型；挂卖推测价值只能 WATCH，不能作为当场现金安全机会。
- **统一最低正式门槛**：普通净利>=50M ISK；非BPC >=2,000 ISK/m³；ROI/正压力和完整深度延续批准口径。高价值合同 >5B 使用原5–8B ACTIONABLE、>=500M、ROI>=10% 等特殊门槛。此提案不改变参数。
- **评分仅排序**：先过不可妥协资格，再按可核实净利润、ROI、订单可成交数量、流动性、物流风险、资本占用和置信度排序；不能因为分数高就绕过 SAFE。

## 5. 扫描与推送两个独立时钟
**完整扫描：** 默认设计为“上轮 COMPLETE/失败结算后，经过短暂冷却启动下一轮完整全量扫描”，初期建议目标每60–120分钟完成一轮，但必须以真实全服分页量和 ESI API限流压力测量决定。不能因指定时钟到点就取消/叠加上轮。超过预算=记录欠账、继续分批或排队，不允许静默把完整扫描降级为 TOP 模式。
**邮件：** 建议每2小时汇总一次，可以配置4小时；每角色每轮至多一个按重要性排序的摘要、多条新实例；没有经发信前复核仍有效的新增机会则不发送。发送前取得官方允许的最新有效市场/合同状态，再运行同样 Gate，撤销已经消失的机会。推送间隔越长，短命捡漏越可能消失，这是明确代价；如需极短时间交易的真正机会，未来可以单独审批紧急邮件策略，默认不启用。
**再提醒：** 默认禁止同 instance 的价格波动/名次变化重复首次推送；只有更换经验证的新执行订单实例（或用户批准的重大变化策略）才生成新事件。合同到期不再提示。
**送达：** 邮件成功时数据库记 sent_at/mail_id；失败保留队列；上游回执超时进入 UNCERTAIN，不自动无脑重试造成重复邮件。一次EVE邮件与一次DB写入不可能天然成为一笔事务，采用Outbox+补偿对账和人工处置。
**存储：** 高吞吐明细存在独立数据库（Cloudflare D1优先评估），Airtable仅同步运行/机会摘要，Notion存经过审核的结论；不再把上百个CSV写回main。

## 6. 关键监控指标与每轮验收
| 指标 | 期望证明的事情 |
|---|---|
| 预期来源/实际完整来源、应读/已读页数 | 全市场数据覆盖率是否达到100%，哪里无法读取 |
| run_id、缓存确认时间、page timestamp、ESI TTL | 当前轮是不是确实重新获取/确认了市场数据 |
| 全服商品/合同/订单总数、precheck数量 | 是否将每个来源全部纳入初筛 |
| 可行候选/完成深验/待验/拒绝数量 | 有没有因为固定Top和超时偷偷丢新机会 |
| 通过Gate总数、老实例/新实例、历史已发、排队待发 | 区分少机会、漏报、正常抑制 |
| 邮件发送数、送达失败/不确定数、平均推送延迟 | 推送系统是否真的可靠 |
| 人工买入数、买入价偏差、售出/持仓、已实现利润、资金周转 | 数值能否对应真正赚到的钱 |

**关键自动回归验收：**
1. 100合格、前10已发、后90全新：后90不可被永远挡在TOP外。
2. 同一商品出现新 source order_id：重新发现/有资格获首次推送；旧 order_id 报价变动仅更新实例版本。
3. 同合同波动 TOP 2→1→2 或跨角色/工作流：同实例只创建1次首次提醒。
4. 任一公开来源缺页、ESI403/429/520、合同过期、source/exit订单失效：不报完整且不可依据错误输入生成MAIL。
5. 同一轮有数万合同与上千市场分页：全量初筛覆盖100%，预算不足明确INCOMPLETE并断点续验。
6. 新旧代码同时影子运行 >=72h，新版没有发送真实邮件；使用至少7天有可信快照的回放，实测新增真实候选和被抑制数。
7. 推送每2–4小时：送出前完整复核，失效机会直接撤销，下一封也不回补已失效旧机会。

## 7. 需要审核的三项参数（不是审批后自动执行）
- 全市场**覆盖范围**：建议包括所有 ESI 可查询公开交易区域订单与全服公开合同，外加已获访问的 4-H/C-J/O4T 玩家建筑，不假装覆盖未授权建筑。
- **扫描节奏**：完整全量优先，目标60–120分钟/轮，真实吞吐实测后定；若无法完成，宁可加长而不缩成TOP。
- **推送节奏**：默认建议2小时合并发送，选4小时也可；短命机会可能在等待期间消失，只有复核仍可执行的机会发送。
