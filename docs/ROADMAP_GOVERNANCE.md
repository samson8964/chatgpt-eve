## 1. 项目北极星

项目不以“扫描器数量”“候选数量”或“邮件数量”为成功指标。唯一主线是：

> 在可控资金、可兑现价格、真实税费/运输/制造成本和可验证流动性约束下，持续发现并执行正期望机会；随后用真实买卖结果验证模型是否真的赚钱。

因此整个系统必须形成：

`广发现 → 深复核 → 统一资格 Gate → 只推送可执行机会 → 实际采购/转移/销售 → Realized Audit → 规则调整`

## 3. 当前生产基线

### 3.1 普通机会最终推送 Gate
- 当前统一最终自动推送最低已验证净利润：**50,000,000 ISK**。
- 低于该值的候选仍可扫描、研究和记录，但不得作为正式用户提醒。
- 非 BPC 机会继续执行：**净利润密度 >= 2,000 ISK/m³**。
- SAFE、ROI、压力测试、流动性、实时深度等原有风控继续有效。
- 扫描层可以使用更低发现阈值；发现阈值不得被误认为最终推送阈值。

### 3.2 BPC 制造正式推送独立严格 Gate
- **4-H 规则保持不变。**
- BPC 扫描仍然广泛发现，但自动邮件采用更严格的独立门槛。
- V2 必须为 **SAFE**，远端最优路径实时净利润 **>=100M ISK**、实时 ROI **>=15%**、压力利润 **>=50M ISK**。
- 同时必须完成 **Jita 制造成本验证**；按 Jita 制造口径，保守净利润 **>=50M ISK**、ROI **>=10%**、压力利润 **>0**。
- 自动邮件显示 **Jita 制造保守利润/ROI**，远端低 SCI 工厂只作为理论参考，不再用“0 运输成本”支撑正式推荐。

### 3.3 高价值合同独立通道
- >5B 的纯多件 item-exchange 合同进入独立引擎。
- **5–8B：ACTIONABLE**
- **8–20B：WATCH**
- **>20B：RESEARCH**
- 只有 ACTIONABLE 且同时满足 **SAFE、保守净利润 >=500M、ROI >=10%、压力情景仍盈利** 才推送。
- 资本舰不再整单排除；按区域公开买单和额外本地风险储备进行保守估值。

### 3.4 角色与经营流
- **MikeChong + LadyBaBa：采购**
- **LadyGuaGua：集中销售**
- 内部角色转移不应被视为利润或成本变化。
- 实际利润审计必须跨角色归并后再做 FIFO/批次匹配。

### 3.5 运行边界
- GitHub push 只做验证，不应触发真实生产扫描/发信。
- Cloudflare/manual cadence 承担生产扫描。
- 单通道故障应降级而非污染整个机会系统。
- 真实购买、资金投入、资产转移仍由用户决定与执行。

## 5. 当前唯一主线：P3 Realized Profit Closed Loop

现有 `trade_realized_audit.py` 和 `.github/workflows/trade-audit.yml` 已证明三角色数据可读取，并已经得到第一版跨角色实现利润结果。

但当前治理上仍不能直接把第一版 realized P&L 当成最终经营真相，原因包括：
- 采购角色与销售角色不同，需要跨角色批次归并；
- 可能存在非捡漏来源的同类库存，被 FIFO 错配到捡漏批次；
- BPC/制造链尚不能仅靠市场成交直接闭环；
- 手动 workflow 证明了能力，但尚未形成稳定的审计节奏和异常门禁。

### P3 验收顺序
1. **库存来源隔离**：给审计批次增加“来自正式推送机会”的确定性标识；无法证明来源的同类库存不得自动归因。
2. **异常交易校验**：对极端低成本/极端高 ROI、跨角色大额转移、合同多件成本分摊建立 DANGER/REVIEW 标志。
3. **闭环覆盖率**：区分“已实现、仍持仓、制造消耗、无法归因”，不把未匹配资产自动当亏损。
4. **可重复运行**：同一历史窗口重复审计应得到稳定结果，不因状态文件或数据刷新产生大幅漂移。
5. **再决定调度**：在结果可靠后，再决定固定审计频率；治理阶段不为了“自动化看起来完整”而提前制造定时噪音。

## 6. 决策指标

以后项目优化优先看以下指标，而不是扫描量：

- **Realized Net Profit**：真实已实现净利润。
- **Realized ROI on Cost**：按已实现成本计算的实际 ROI。
- **Capital Days / Turnover**：资金被占用多久。
- **Execution Rate**：推送机会中真实采购比例。
- **Close Rate**：采购后完成出售/兑现比例。
- **False-positive Rate**：被实际证据推翻的正式机会比例。
- **Attribution Coverage**：采购批次中有多少能被可靠分类为已实现/持仓/制造/其他。
- **Channel Contribution**：普通合同、BPC制造、多件、4-H、C-J、V3、高价值合同分别贡献多少真实利润。

## 7. 变更治理

### 可直接调整
- bug 修复、重试、日志、缓存、CI；
- 不改变经济含义的性能优化；
- 不改变用户提醒口径的可观测性改善。

### 必须记录 Decision
- 最终净利润/ROI/利润密度门槛变化；
- ACTIONABLE/WATCH/RESEARCH 资金分层变化；
- 新增或删除正式扫描通道；
- 估值口径、运输/税费/制造成本口径变化；
- 推送对象、采购角色、销售角色变化；
- realized P&L 归因模型变化。

### 必须由用户决定
- 真实购买；
- 资金上限大幅提高；
- >8B 合同进入自动可执行范围；
- 新角色/新结构需要登录或 OAuth/ESI 授权；
- 任何会直接移动资产或产生不可逆交易的动作。

## 8. Roadmap Review Triggers

出现以下任一情况，路线图必须重新审查：
- 当前 50M 最终推送门槛被用户修改；
- 可用资金明显偏离当前约 8B 的高价值合同设计基线；
- 某通道连续出现“游戏内明显机会但系统长期漏扫”；
- realized audit 证明某通道长期实际亏损或实际 ROI 与模型系统性偏离；
- 生产总运行时间逼近调度周期，导致下一轮重叠；
- ESI/CCP API、税费、合同/市场机制发生重大变化；
- 用户改变采购/销售角色或主要活动区域。

## 9. 当前下一步

**不要继续无边界增加扫描器。**

当前开发资源优先级固定为：
1. **P3 实际利润归因可靠性**
2. **P4 只复核仍真实存在的经济模型技术债**
3. **P5 用 realized P&L 做通道与资金优化**
4. 新扫描方向只有在能填补已证明的漏扫类型时才进入正式路线图

这套路线图从 2026-10-04 起作为 EVE 捡漏项目的正式治理基线。
